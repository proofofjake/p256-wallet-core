# Security review, round 2

Review of `p256-wallet-core` v0.2.1 at commit `2c37779` (18 Oct 2026), following the v0.2.0 fixes for
`ISSUES.md`. This round:
- re-checked every claimed fix independently;
- reviewed the new surfaces: `verify_registration`, the self-call allowlist, paymaster handling, `sanitize` and
  `check_wallet_record`;
- checked the core against the deployed contracts and against external reference data.

New findings continue the numbering from `ISSUES.md` (F15 onwards). Each comes with the behaviour that reproduces
it, so it can be turned into a test.

**Resolution, 19 Oct 2026 (v0.3.0):** every finding is fixed, each with a `finding_f<N>_…` test in
`tests/security.rs`, and every efficiency and readability suggestion is applied except where noted. Each section
ends with a **Status** line. (This report was `SECURITY-REVIEW-2.md`; `ISSUES.md` is now
`audits/2026-10-18-review-1.md`.)

## F15 · Critical · Any operation can add an attacker's P-256 key as an owner

**Where:** `smart_wallet::classify_self_call` (`SelfCall::AddOwnerPublicKey`, `SelfCall::RemoveOwnerAtIndex`),
`api::check_operation`, `review::describe_call`

**What happens:** the F2 fix refuses `addOwnerAddress` on the grounds that "this wallet only accepts security keys
as owners". But `addOwnerPublicKey` accepts any valid P-256 point, and anyone can generate one in software. Onchain
there's no attestation and no hardware requirement. So adding an attacker's P-256 key is exactly as much a takeover
as adding an attacker's address, and the core reviews and signs it for any operation, whoever built it.
`removeOwnerAtIndex` is allowed the same way, so one batch can add an attacker key and remove both real owners. The
core signs that batch too.

**Reproduced end to end against the deployed contracts** (Coinbase Smart Wallet and EntryPoint v0.6, Base Sepolia
state, nothing broadcast):
1. A wallet with two owners and 100 ETH was deployed through the real factory.
2. An operation whose only call was `addOwnerPublicKey(<attacker's software key>)` was built, reviewed and signed by
   the core. The review read:
   ```
   From: 0xdCE3…DC3c
   Network: Base Sepolia
   Add owner key: P-256 0xaec36e41…cab5de91
   Effect: The new key can sign for this wallet on this network
   ```
3. The EntryPoint executed it, and `isOwnerPublicKey` returned true for the attacker's key.
4. The attacker built a transfer of 99.9 ETH to their own address. The core signed it with the attacker's key as
   owner #2, given only the public initial-owner list. The EntryPoint executed it, and the wallet was drained.

**Impact:** any dapp the extension relays a transaction for, a compromised app build, or a malicious bundler-side
flow that gets one approval can take the wallet over permanently. The review gives a 128-character hex key, with no
way for a user to tell their own new key from an attacker's.

**Fix:**
- Treat owner changes as the app's own flow, never as something a third party can request:
  - The core only signs `addOwnerPublicKey` for a key the caller proves the user just registered. For example,
    `review_user_operation` / `sign_user_operation` take `new_owner_keys: Vec<PublicKey>` from a fresh
    `verify_registration`, and refuse any `addOwnerPublicKey` whose key isn't in that list.
  - Require an owner change to be the only call in its operation. No batching with transfers or other owner
    changes.
  - Refuse a `removeOwnerAtIndex` that removes the key signing the operation, or that would leave fewer than one of
    the wallet record's keys.
- In the glue checklist, require that the extension rejects any dapp-originated call whose target is the wallet
  itself, before it reaches the core.

**Status:** fixed. `policy::check_operation` (used by both review and signing) allows a self-call only for
`addOwnerPublicKey` of the key passed as the new `new_owner` argument, and only as the operation's sole call.
Apps pass `new_owner` from their own add-key flow, straight from `verify_registration`, and `None` everywhere else,
so an operation built by anyone else that adds a key is refused (`CoreError::Refused`). `removeOwnerAtIndex` is now
refused outright, like `removeLastOwner`: neither app removes owners, so there's nothing to allow. The review of the
allowed call reads "The key you just registered can sign for this wallet on this network". The README checklist
adds the extension rule. Test: `finding_f15_only_the_key_just_registered_can_become_an_owner`, which replays the
reproduction (single add, add-plus-remove batch, removal alone).

## F16 · Medium · Common approval and drain calls aren't recognised

**Where:** `review::describe_call`

**What happens:** only ERC-20 `transfer` and `approve` are decoded. These reviewed as "Contract call / Function:
Unknown (0x…)":
- `setApprovalForAll(address,bool)`: every NFT in a collection;
- `increaseAllowance(address,uint256)`, including `uint256.max`;
- Permit2 `approve(address,address,uint160,uint48)`;
- `transferFrom(address,address,uint256)`, with the wallet as `from`.

**Impact:** these are the most common wallet-drain patterns. A user who's learned that "Unknown" usually means a
harmless dapp call will approve them.

**Fix:** decode these by selector and shape, the way `approve` is today. Show "Approve ALL items in this collection
to 0x…", "Increase allowance: Unlimited", and the Permit2 token, spender, amount and expiry. Treat them as approvals
in any future warnings.

**Status:** fixed. `review::decode_call` decodes these by selector and exact shape (canonical encoding, a
bool of 0 or 1, Permit2's `uint160` / `uint48` ranges), then `render` shows them: "Approve: ALL items in this
collection, including ones received later" with the operator (and "Revoke" for `false`); "Increase allowance by:
Unlimited"; Permit2's token, spender, amount and UTC expiry, naming Permit2 at its canonical address; and
`transferFrom` with "(this wallet)" marked on the `from`. ERC-721 `safeTransferFrom` (both forms) and ERC-1155
`safeTransferFrom` are decoded too. Anything that doesn't decode cleanly stays an "Unknown" contract call. ERC-1155
`safeBatchTransferFrom` isn't decoded yet; it's tracked in `ISSUES.md`. Test:
`finding_f16_approval_and_drain_calls_are_recognised`.

## F17 · Medium · The per-key PIN requirement is only as strong as the stored data

**Where:** `OwnerKey.require_user_verification`, `api::check_wallet_record`, `webauthn::signature_data`

**What happens:** whether a key needs its PIN is read from the `OwnerKey` the app passes in. A wallet record restored
from a backup file, or edited in app storage, with `require_user_verification` flipped to `false` passes
`check_wallet_record`. After that, signing accepts a touch-only response from a key the user protected with a PIN.

**Impact:** someone with the YubiKey and write access to the app's storage or backup file (or the ability to get a
doctored backup restored) can sign without the PIN. That's the case the PIN option exists for.

**Fix:**
- When the user asks for a PIN, require `pin_enforced_by_key` at registration (request `credProtect` level 3 and
  refuse the registration if the key didn't apply it). The key then enforces the PIN itself, whatever any stored
  flag says.
- Treat `require_user_verification` as a display hint, not the control.

**Status:** fixed as suggested. `verify_registration` with `require_user_verification` now also refuses a key
that didn't apply `credProtect` level 3 (`CoreError::Refused`, with a message saying which keys can). The flag stays
on `OwnerKey` and signing still checks it, documented as defence in depth rather than the control. Keys registered
with a PIN before v0.3.0 keep working; the apps label them "PIN checked by this app". The iOS app no longer offers
a PIN, because iOS has no API to request `credProtect`; the browser extension requests it and lets the core refuse
keys that don't apply it. Test: `finding_f17_pin_keys_must_enforce_the_pin_themselves`.

## F18 · Low · `sanitize` misses 307 invisible Unicode characters

**Where:** `review::sanitize`, `review::is_invisible_or_bidi`

**What happens:** `sanitize` escapes characters from a hand-written deny-list. Checked against the Unicode 18.0
Character Database (every default-ignorable code point and every format, Cf, character), 307 assigned characters
pass through unescaped. They include:
- variation selectors U+FE00–FE0F and U+E0100–E01EF;
- Mongolian free variation selectors U+180B–180F;
- the deprecated format controls U+206A–206F, including the symmetric-swapping and digit-shape switches;
- Arabic and Kaithi number signs U+0600–0605 and U+110BD;
- Egyptian hieroglyph and shorthand format controls.

**Impact:** limited. These can make two strings look identical while differing, or change how neighbouring
characters render, inside token symbols and string arguments. A deny-list will keep falling behind Unicode.

**Fix:** invert it. Escape everything except an allow-list (letters, marks, numbers, punctuation, symbols and the
ASCII space), or generate the deny-list from `Default_Ignorable_Code_Point` + `Cf` at build time.

**Status:** fixed by inverting it. `src/unicode_table.rs` is generated by `scripts/unicode-table.py` from
Unicode 18.0.0 `DerivedGeneralCategory.txt` and `DerivedCoreProperties.txt`. It lists what is shown as itself:
assigned L, M, N, P and S characters that aren't `Default_Ignorable_Code_Point`, plus the ASCII space (and minus
U+2800 BRAILLE PATTERN BLANK, which renders blank). Everything else is escaped, including unassigned code points, so
the table can only fall behind Unicode in the safe direction. Escapes are written into the output buffer, without
per-character allocations. Test: `finding_f18_invisible_characters_are_escaped`; a unit test also checks every
`char::is_control` character is escaped.

## F19 · Low · Batch summary rows show unverified function names without the mark

**Where:** `review::contract_call` (the returned summary `format!("Call {}", signature.name)`)

**What happens:** in a batch, each call's one-line summary ("Call 2 of 2") uses the supplied function name with no
"(unverified)". With `burn(uint256)` calldata and `collate_propagate_storage(bytes16)` in the signature list, the
summary row reads `Call collate_propagate_storage`. The "(unverified)" mark appears only on the detail line below.

**Fix:** mark the summary too ("Call collate_propagate_storage (unverified)"), or summarise as "Contract call"
whenever the name isn't verified.

**Status:** fixed: the summary reads "Call collate_propagate_storage (unverified)". Test:
`finding_f19_batch_summaries_mark_unverified_names`.

## F20 · Low · Duplicate-key checking in CBOR is quadratic

**Where:** `cbor::item`, the map branch (`pairs.iter().any(...)`)

**What happens:** each new key is compared with every earlier one. A registration carrying a 20,000-entry map
(about 60 KB) takes about 0.38 s to reject in an optimised native build. It's slower in WebAssembly, and the time
grows with the square of the map's size.

**Impact:** a malformed or malicious registration response can stall the UI thread. It needs a misbehaving
platform, so the severity is low.

**Fix:**
- Require CTAP2 canonical ordering: map keys strictly increasing in their encoded form. That's one comparison per
  key, and it rejects duplicates and non-canonical encodings together.
- Also cap map and array sizes (a COSE key has under ten entries).

**Status:** fixed, both parts. Arrays and maps hold at most 32 items. CBOR the authenticator encodes (the COSE
key and extension outputs) is read as CTAP2 canonical: shortest-form arguments, no tags, and map keys strictly
increasing in canonical order, one comparison per key. The attestation object around it is assembled by the
browser or OS, which WebAuthn doesn't require to be canonical, so there only duplicates are refused (by a scan
bounded by the cap). Test: `finding_f20_huge_and_non_canonical_cbor_is_refused_quickly`: the 20,000-entry map is
refused without being read.

## F21 · Low · `check_wallet_record` allows two keys with the same owner index

**Where:** `api::check_wallet_record`

**What happens:** duplicate credential IDs are refused, but two different keys both claiming owner #3 (an index
past the initial owners) are accepted.

**Impact:** a damaged or edited backup is accepted. One of the two keys then fails onchain.

**Fix:** refuse repeated `owner_index` values, as is already done for credential IDs.

**Status:** fixed, per chain. Owners added after deployment exist only on the chain where they were added, and
each chain has its own `nextOwnerIndex`, so two keys can legitimately hold owner #2 on two different chains. Refusing
every repeated index would reject real backups. `OwnerKey` now carries `added_on_chain_id` (both apps already
stored it), and `check_wallet_record` refuses two keys with the same index on the same chain. The shared
`check_owner_key` also requires initial owners not to name a chain, and later owners to name one. Signing now
refuses a key added on another chain with a clear error, instead of an onchain rejection. Test:
`finding_f21_two_keys_cant_share_an_owner_slot`.

## F22 · Info · Cross-origin and duplicate-key `clientDataJSON` are accepted

**Where:** `webauthn::signature_data`

**What happens:** responses with `"crossOrigin":true` (made inside an iframe on another site), or with duplicate
`challenge` / `type` keys, are accepted. The deployed wallet's verifier accepts exactly the same set, and real
browsers never emit duplicate keys, so the two agree.

**Fix (defence in depth):** now that the RP ID is pinned, refusing `"crossOrigin":true` costs nothing for the
wallet's own pages and extension.

**Status:** fixed. `webauthn::signature_data` refuses `"crossOrigin": true` (whitespace tolerated), and
`clientDataJSON` where `"type"` or `"challenge"` appears more than once. Test:
`finding_f22_cross_origin_and_ambiguous_client_data_is_refused`.

## Verified

These were tested independently this round and hold:

- **Calldata decoding matches the deployed wallet.** For random and malformed `execute` / `executeBatch` calldata,
  the real Coinbase Smart Wallet executed exactly the calls the core decoded, in every case the core accepted (220
  cases, no divergence). The core accepted nothing the wallet then failed on, and refused many encodings the wallet
  would have run, which is the safe direction.
- **The core and the onchain verifier agree on every response shape tested.** That covers Safari, Chrome (with the
  extra key), extension origins, Android, cross-origin iframes, reordered keys, and seven malformed or adversarial
  shapes.
- **ECDSA signature handling is correct across the standard edge cases:** strict DER, out-of-range and zero values,
  BER encodings, and high-s.
- **No input panics any exported function,** the new v0.2 functions included.
- **The v0.2 fixes hold under independent tests:** F1, F6–F10, F12 and F14 as claimed. F2's refusals hold inside
  batches, for checksum and lowercase forms of the sender, and for nested `execute` / `executeBatch` self-calls.
  F8 refuses swapped and reordered owners.

## Efficiency and readability

The core is small and careful. These would make it easier for a reviewer to read in one sitting, and remove a few
places where two copies of the same rule could drift apart.

1. **Check an operation once, then use the result.** A single review currently decodes the calldata three times
   (`check_operation`, `review_user_operation`, `review::describe`) and parses the paymaster twice.
   - Introduce `fn check(op, chain_id) -> Result<CheckedOperation>`, returning the decoded calls, paymaster,
     deployment and chain.
   - Make `review_user_operation` and `sign_user_operation` both consume it.
   - That's one pass, and it guarantees review and signing apply the same policy (today they agree because the same
     helpers are called in two places).
2. **Split `api.rs` (783 lines).** Three files would each be readable in one sitting:
   - record ↔ internal conversions into `convert.rs`;
   - the wallet-record and owner-key checks, the self-call allowlist and paymaster policy into `policy.rs`;
   - `api.rs` itself as the thin exported surface.
3. **Write the owner-key check once.** The rule "a key claiming an initial owner's index must be that owner" is
   written separately in `wrapped_signature` and `check_wallet_record`. `record_owners` is also re-implemented
   inline in `check_wallet_record`. Use one `check_owner_key` and `record_owners` in both.
4. **Look a chain up without rebuilding them all.** `chains::all()` builds every chain config, token lists included,
   and is called twice per review just to find one chain's name and paymasters. Add `chains::by_id(id)` over static
   data.
5. **Name repeated constants once:**
   - `"transfer(address,uint256)"` appears 6 times, `"approve(address,uint256)"` 3, and `"addOwnerAddress(address)"`
     4. Put selectors in one module.
   - The P-256 half-order constant is written out 3 times; make it one `P256_HALF_N`.
   - `hex20` / `hex32` can be one `const fn hex<const N: usize>`.
6. **Separate decoding from display in the review.** `review::describe_call` decides what a call is and formats it in
   the same branches. Decode into a `CallKind` enum first (`SendEth`, `Transfer`, `Approve`, `SelfCall`, `Contract`,
   …), then render. The F16 approval families slot in as variants, and each can be tested without string matching.
7. **CBOR:** the canonical-order check in F20 replaces a quadratic scan with a linear one.
8. **`sanitize`:** it builds a `format!` string for every escaped character. Writing into the output buffer
   (`write!` or `char::escape_unicode`) avoids those allocations. An allow-list (F18) is also shorter to read.
9. **Generate the WebAssembly wrappers.** `wasm.rs` (229 lines) mirrors every `api` function by hand. A small macro
   would cut it to a list of names, and adding an API function couldn't leave TypeScript behind.
10. **Errors:** refusals are prefixed "Refused:" in some places and not others. A distinct `CoreError::Refused` kind
    would let the apps show "the wallet won't sign this" differently from "the input is malformed".
11. **`ISSUES.md`:** at 337 lines it mixes open and resolved items. Keep only open issues there, and move resolutions
    to a `SECURITY.md` history or the changelog.

**Status of these suggestions (v0.3.0):**
1. Done. `policy::check_operation` returns a `CheckedOperation` (calls, paymaster, chain), and both
   `review_user_operation` and `sign_user_operation` go through it.
2. Done: `convert.rs` (records ↔ internal types), `policy.rs` (operation policy, owner-key and wallet-record
   checks) and `api.rs` (the exported surface, about 290 lines before its tests).
3. Done: `policy::check_owner_key` and `policy::record_owners` are used by signing and `check_wallet_record`.
4. Done: `chains::by_id` over static data. `chains::all` builds the records only for the apps.
5. Done: `functions.rs` holds every signature, `webauthn::P256_HALF_N` the half-order, and `hex::array` replaces
   `hex20`/`hex32`.
6. Done: `review::CallKind`, decoded by `review::decode_call` and rendered by `review::render`.
7. Done (F20).
8. Done (F18).
9. Done: `wasm.rs` generates every wrapper from one `export!` list. Arguments and results cross through serde,
   which also lets chain IDs be `u64` in TypeScript.
10. Done: `CoreError::Refused` for policy refusals (self-calls, unknown account functions, foreign deployments,
